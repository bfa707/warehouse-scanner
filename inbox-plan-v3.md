# Омниканальный инбокс для приёма заказов из соцсетей — план v3

> Документ для внешнего технического ревью. Ниже: контекст существующей системы, требования,
> предлагаемая архитектура, гейты, стоимость, известные ограничения и открытые вопросы.
> Просьба проверить схему на скрытые допущения, реалистичность и упущенное.
> Все утверждения о возможностях Chatwoot и Meta API помечены как «требует проверки», где не подтверждены.

---

## 1. Контекст: что уже работает

Компания — розничная торговля одеждой, юрлицо в Латвии (ЕС). Заказы приходят из переписок в соцсетях.

**Существующая система (в бою, не переписывается):**
- Google Sheets как база: заказы, остатки, клиенты.
- Google Apps Script веб-аппка — интерфейс работников склада: приёмка, выдача, сканирование
  штрихкодов, генерация подтверждений, инвойсы, доставка.
- Аппка открывается на телефоне через лаунчер: иконка на домашнем экране → iframe-embed
  на весь экран без панели Safari. Работники привыкли к этому входу.
- Есть рабочий паттерн очередей записи в таблицу (борьба с конкурентными запусками, LockService).

**Как заказы попадают в таблицу сейчас:** работник читает Директ/Мессенджер в родных приложениях
и вручную переносит данные в таблицу. Это и есть узкое место, которое решается.

**Каналы и доли:**
- Instagram Direct — ~80%
- Facebook (Messenger + комментарии к постам, уводимые в Messenger) — ~15%
- WhatsApp — <5%
- Отдельно: прямые эфиры в Instagram (см. раздел 8)

**Объём:** порядка 2000 переписок в месяц. Пики — при выкладке новой коллекции.

**Операторов:** 3 человека. Работают **80% времени с телефона (iPhone, через лаунчер-иконку),
20% с компьютера.**

## 2. Требования

1. Один список входящих со всех каналов, три оператора не наступают друг на друга
   (назначение диалога, атрибуция «кто ответил», прочитано/не прочитано).
2. Ответ клиенту уходит в его родной мессенджер.
3. Оформление заказа происходит рядом с перепиской, без ручного копирования ника.
4. **Работник не должен уходить в сторонний интерфейс** — вход через нашу иконку,
   наш домен, наш бренд.
5. Существующий пайплайн Apps Script (подтверждение, инвойс, доставка) сохраняется без переписывания.
6. **Безопасность аккаунта Instagram:** только официальные API Meta. Никаких неофициальных
   библиотек, эмуляции входа, сторонних сендеров с логином/паролем.
7. Работа преимущественно с телефона (см. п. «операторов» выше) — это жёсткое ограничение,
   а не пожелание.

## 3. Предлагаемая архитектура

Chatwoot используется как **готовый движок инбокса**, а не как «труба» к собственному фронтенду.
Собственный фронтенд инбокса решено не писать: список диалогов, живое обновление, вложения,
unread, назначение, история, окно 24 ч — это месяцы разработки и вечная поддержка того,
что уже существует.

Собственная разработка сводится к одному: **форма оформления заказа, встроенная в панель диалога**
(механизм Chatwoot «Dashboard App» — iframe в правой панели, получающий контекст диалога
через `postMessage`). Внутри iframe — существующая Apps Script веб-аппка.

| Компонент | Роль |
|---|---|
| **Chatwoot** | Подключение каналов (IG Direct, FB Messenger, FB-комментарии), приём вебхуков Meta, менеджмент токенов, окно 24 ч, вложения. Родной инбокс для 3 агентов. |
| **Dashboard App** (Apps Script веб-аппка в iframe) | Форма заказа в панели диалога. Получает ник/канал/id диалога через `postMessage`, подставляет клиента автоматически. |
| **Google Sheets + Apps Script** | Пайплайн заказов без изменений: заказы, подтверждения, инвойсы, доставка. |

**Потоки:**
- **Входящее:** клиент пишет → Meta → Chatwoot → диалог в инбоксе у трёх агентов.
- **Ответ:** агент отвечает в интерфейсе Chatwoot → уходит клиенту в его мессенджер.
  Отправка через общий Application API **не используется** — она убивает атрибуцию
  и даёт коллизии при трёх операторах.
- **Заказ:** агент в панели диалога заполняет форму (Dashboard App) → строка в Google Sheet →
  существующий пайплайн инвойсов.

**Важно (исправлено против предыдущей версии плана):** заказ создаётся **только** осознанным
действием работника через форму. Автоматическая запись строки в таблицу по вебхуку
`message_created` отвергнута — она даёт строку на каждое сообщение, а не на заказ.
Как следствие, отдельное «реле вебхуков» на VPS в базовой схеме не требуется.

## 4. Гейты и фазы

Два первых гейта могут отменить всю схему, они дешёвые и делаются до любой разработки.

### ГЕЙТ 1 (блокирующий) — работает ли схема на телефоне
80% работы с iPhone. Вся конструкция держится на панели диалога с встроенной формой.
Есть обоснованное подозрение, что **Dashboard Apps не отображаются в мобильном приложении
Chatwoot** — это может быть фича только веб-дашборда. **Требует проверки.**

Проверить: открыть Chatwoot с iPhone в мобильном приложении и в мобильном Safari,
убедиться, что панель с Dashboard App видна и пригодна к работе на узком экране.

Если не работает — схема пересматривается целиком (варианты: работа только через мобильный
браузер; отдельная лёгкая мобильная надстройка; возврат к идее собственного фронтенда).

### ГЕЙТ 2 (блокирующий) — тариф
Подтвердить у Chatwoot письмом, что **Dashboard Apps входят в выбранный план**, а не только
в старшие. **Требует проверки.** Если нет — конструкция пересобирается.

### ГЕЙТ 3 (технический) — Apps Script внутри cross-origin iframe
Встраивание включается через `setXFrameOptionsMode(ALLOWALL)`, но проблема не в этом,
а в Google-логине внутри стороннего iframe: Safari блокирует третьесторонние куки,
поэтому авторизация Google почти наверняка не отработает.

Решение принимается заранее, без экспериментов с логином: публиковать веб-аппку
с доступом «по ссылке» + собственный подписанный токен для идентификации агента.

### Фаза 1 — каналы (без своего кода)
Подключить Instagram Direct (OAuth, бизнес-аккаунт + FB-страница), Facebook Messenger,
настроить FB-комментарии → private reply в Messenger. Проверить на триале: входящие падают,
ответы уходят, назначение между тремя агентами работает.

### Фаза 2 — форма заказа
Оформить существующую Apps Script-форму как Dashboard App. Принять `postMessage`
с контекстом диалога. **Ключ связки — IGSID, не ник.** Синтаксис payload сверить с доками.

### Фаза 3 — решение о хостинге
Принимается после подтверждения гейтов и фазы 1 (см. раздел 5).

### Фаза 4 — WhatsApp (отложено)
<5% объёма. Отдельный номер + BSP. Не блокировать им запуск.

## 5. Стоимость и развилка Cloud vs self-hosted

| Статья | Cloud | Self-hosted (EU) |
|---|---|---|
| Лицензия | ~$19 × 3 агента = **$57/мес** | Community Edition — $0 |
| Сервер | — | ~€10–15/мес (Hetzner, Германия/Финляндия) |
| IG/FB messaging | бесплатно | бесплатно |
| Meta App Review | не требуется (используется приложение Chatwoot) | **требуется своё** (`pages_messaging`, `instagram_manage_messages`) — недели |
| Свой домен, логотип, убрать чужой бренд | **невозможно** | да |
| Данные | AWS US | ЕС |
| Поддержка/обновления | на них | на нас |

**Ключевой конфликт:** требование №4 (работник не выходит из нашей аппки, наш бренд и домен)
**на Cloud невыполнимо** — работник открывает чужой домен и видит чужой бренд.
Полное выполнение требования возможно только на self-hosted. **Требует проверки** —
подтвердить, что на Cloud действительно нет белой этикетки на доступном плане.

При трёх агентах self-hosted одновременно дешевле (~€12 против $57) и снимает вопрос
локации данных. Единственная реальная цена — свой App Review.

**GDPR отдельно:** хостинг Chatwoot Cloud в США при обработке персональных данных клиентов
из ЕС покрывается DPA + SCC, это стандартная практика для юрлица ЕС и **не является блокером**.
То есть выбор диктуется брендом и ценой, а не правовым риском.

**Предлагаемый порядок:** триал Cloud для проверки гейтов и живости каналов; параллельно
запустить App Review; в бой выходить на своём сервере в ЕС.
**Просьба к ревьюеру оценить, не переоценена ли трудоёмкость своего App Review
и не разумнее ли остаться на Cloud, приняв компромисс по бренду.**

## 6. Известные ограничения (приняты сознательно)

1. **Instagram: стикеры-вопросы в сторис API не отдаёт.** Клиент появляется в инбоксе
   только когда перейдёт в Директ. Не критично — сделка всё равно в Директе.
2. **Голосовые сообщения Instagram через API не вытянуть** — приходят как UNSUPPORTED
   без ссылки на файл. Принято: фиксируем факт «было голосовое», слушаем в нативном IG.
   Текст, фото, видео, файлы — тянутся нормально.
3. **CDN-ссылки на медиа живут недолго** — скачивать сразу. В этой схеме забота Chatwoot,
   но при собственном экспорте истории это наша проблема.
4. **Google Apps Script — не живой бэкенд** (лимиты, конкурентные запуски, 302-редирект
   на вебхуках). Остаётся под форму и пайплайн заказов.

## 7. Обязательные технические детали

- **Human Agent tag.** Расширяет окно ответа клиенту с 24 часов до 7 дней. Для приёма заказов
  критично: без него поздние ответы тихо не доставляются. **Требует проверки:** ставит ли
  Chatwoot этот тег сам при ответе агента. Если нет — на Cloud это **не исправить**,
  только на self-hosted. Дополнительный аргумент за свой сервер.
- **Видимый таймер окна 24 ч** для работника, иначе — молчаливые недоставки.
  Проверить, есть ли нативно; если нет — вывести в панели формы.
- **Идемпотентность.** Главная ловушка не ретраи, а то, что событие о новом сообщении приходит
  и на **собственные исходящие ответы**, и на приватные заметки. Фильтровать по типу сообщения.
  (В существующей системе уже случались дубли записей журнала — те же грабли.)
- **IGSID ≠ username.** Ник меняется, IGSID — долговечный идентификатор, но стабилен
  **в пределах одного приложения**: при смене Cloud → self-hosted (другое Meta-приложение)
  идентификаторы поедут. **Это важно для миграции — просьба ревьюеру оценить последствия
  и способ переноса связки «клиент → заказ».**
- **Склейка контактов.** Один и тот же человек в IG и FB — два разных контакта.
  Нужна ручная или автоматическая склейка, иначе история заказов рвётся.
- **Экспорт истории** против vendor lock-in: периодическая выгрузка через API в своё хранилище.
- **Rate limits Meta:** отправку выполняет Chatwoot, собственная очередь исходящих не нужна.
  Вопрос — справляется ли Chatwoot на пиках при дропе коллекции.

## 8. Прямые эфиры — отдельный трек, вне текущего плана

**Как сейчас:** работник смотрит эфир в Instagram и вручную копипастит ники и заявки
из комментариев в Google-таблицу.

**Факты:** эфиры проводятся **только в Instagram**. Комментарии прямого эфира — эфемерная
поверхность, официальный API Meta их не отдаёт (для Facebook Live такая возможность существует,
для Instagram — нет). Chatwoot их не видит и видеть не может.

**Вывод:** проверять доступность полей API бессмысленно, официального пути нет.
Автоматизация невозможна без неофициальных инструментов, что запрещено требованием №6.

**Что реально можно сделать (позже, вне этого плана):** заменить копипаст свободного текста
узкой формой быстрого ввода — два поля (ник + код вещи), валидация по остаткам, блокировка
позиции по принципу «кто первый» через LockService. Это ускоряет ручной ввод и снижает ошибки,
не требуя API. OCR потока эфира отвергнут: ники распознаются ненадёжно, а именно ник критичен.

Владелец: «эфиры — отдельная история, вернёмся позже».

## 9. Открытые вопросы

1. Отображаются ли Dashboard Apps в мобильном приложении Chatwoot и в мобильном Safari? (Гейт 1)
2. Входят ли Dashboard Apps в стартовый платный план? (Гейт 2)
3. Возможна ли белая этикетка (свой домен/логотип) на Cloud, или только self-hosted?
4. Ставит ли Chatwoot Human Agent tag автоматически при ответе агента?
5. Точный формат payload `postMessage` для Dashboard App.
6. Трудоёмкость собственного Meta App Review для self-hosted в 2026 — реально ли это недели,
   и какие подводные камни для латвийского юрлица с пройденной Business Verification.
7. Как переносится связка «клиент → заказ» при миграции Cloud → self-hosted,
   если IGSID привязан к приложению.
8. WhatsApp (после запуска): новый номер или миграция существующего; какой BSP и его наценка.

## 10. Что просим проверить у ревьюера

1. **Не упущено ли главное ограничение — мобильная работа.** 80% времени работник на телефоне.
   Выдерживает ли предложенная схема это, и если нет — какая альтернатива.
2. **Верен ли отказ от собственного фронтенда инбокса** при трёх операторах и 2000 переписок/мес,
   или требование «свой бренд, свой домен» настолько важно, что оправдывает разработку.
3. **Развилка Cloud vs self-hosted** — правильно ли расставлены веса
   (бренд + цена + Human Agent tag против трудоёмкости своего App Review).
4. **Не осталось ли скрытых допущений** в схеме встраивания Apps Script в чужой iframe
   (авторизация, куки в Safari, лимиты Apps Script при трёх одновременных пользователях).
5. **Что упущено полностью.**
