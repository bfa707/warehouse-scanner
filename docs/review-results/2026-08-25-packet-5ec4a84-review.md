## Краткий итог

Правка закрывает несколько локальных веток прошлого ревью, но три заявленные гарантии ещё не выполняются на уровне жизненного цикла:

- подтверждённый повтор перестал быть идемпотентным: повтор того же POST после потерянного ответа создаёт ещё один документ без нового согласия;
- owner-gate принимает обычный трёхдневный простой за смерть триггера и снова допускает старые триггеры сотрудников;
- L/M выбирается как резерв не только для магазинного клиента, хотя эти колонки являются общим снимком прежних E/F, а пользовательское меню вообще обходит новую развилку.

Зелёные тесты и 324 убитые мутации проверяют наличие новых веток, но не исполняют эти последовательности состояний.

## Findings

### HIGH-1 — `repeatOk` отключает идемпотентность подтверждённого повтора: повтор потерянного ответа создаёт следующий документ

**Где:** `Код.js:7438-7452`, `Код.js:8056`, `Код.js:10927-10930`, `Код.js:13752-13754`

До правки `attemptId` отвечал за важную гарантию: повтор одного и того же запроса после потерянного ответа находил надгробие и возвращал прежний файл. Теперь любой вызов с `repeatOk === true`:

1. полностью пропускает `_invJGetDone_()` на `Код.js:7452`;
2. передаёт `repeatOk` в `_invResumePlan_()`;
3. для закрытой записи той же попытки принудительно получает `mode: 'new'`, потому что `mine` вычисляется как `sameAttempt && !repeatOk`.

В результате согласие является не одноразовым разрешением, а постоянным обходом обеих проверок для каждого транспорта того же запроса.

**Воспроизведение:**

1. Заказ уже имеет инвойс; приложение показывает вопрос о повторе.
2. Человек отвечает «Да», приложение отправляет `attemptId=A, repeatOk=true`.
3. Сервер создаёт `R6-101`, закрывает попытку `A`, но HTTP-ответ теряется.
4. Приложение повторяет тот же POST с теми же `attemptId=A, repeatOk=true`.
5. Надгробие снова не читается, закрытая запись снова трактуется как `new`, создаётся `R6-102` без второго вопроса человеку.

Core guard не спасает: он сериализует одновременно живые исполнения, но после завершения первого запроса уже снят. Последовательный сетевой retry проходит.

Тест `tests/test-repeat-invoice-guard.js`, раздел 13, проверяет только один вызов с `repeatOk` и утверждает, что он дошёл до создания. Он не закрывает эту новую попытку и не повторяет тот же подтверждённый запрос. `tests/sim-journal.js` также не содержит оборота `repeatOk → close → retry repeatOk`.

**Что исправить:** согласие должно порождать новый устойчивый id новой попытки, который сохраняется при транспортных retry. Первый подтверждённый вызов создаёт документ, а каждый повтор с тем же новым id обязан получать replay. Boolean `repeatOk` не должен безусловно выключать надгробие. Нужен тест полного оборота: old done → consent/new attempt id → close → потерянный ответ → retry того же consent attempt → тот же файл, второго создания нет.

### HIGH-2 — Трёхдневная метка измеряет частоту кликов, а не здоровье owner-trigger; после штатного простоя сотрудник снова может стать исполнителем

**Где:** `Код.js:654-698`, `Код.js:10346-10394`, `Код.js:10459-10470`; caller `setupAll_invoicesProject_()` — `Код.js:575-609`

Heartbeat обновляется только когда owner-trigger обслуживает дверное событие, и не чаще раза в час. Поэтому отсутствие дверей в течение трёх дней неотличимо от удалённого триггера.

**Обычный сценарий без аварии:**

1. В таблице остаются старые триггеры владельца и сотрудников; marker свежий и сотрудников отсекает.
2. Три дня никто не нажимает L/O/R/U или дверь реестра. Триггер владельца исправен, но marker не обновляется.
3. На первом следующем клике сотруднический запуск видит stale marker и получает `run` на `Код.js:10389-10391`.
4. Запуск владельца тоже получает `run` и обновляет marker, но если сотрудник уже первым взял latch, единственным исполнителем становится он.
5. Файлы снова создаются от аккаунта сотрудника — исходный HIGH прошлого круга возвращается после нормального простоя.

Google подтверждает существенную семантику платформы: установленный триггер всегда работает под аккаунтом создателя, а аккаунты не видят триггеры, установленные друг другом ([Installable Triggers](https://developers.google.com/apps-script/guides/triggers/installable)). `getEffectiveUser()` для установленного триггера действительно обозначает его создателя ([Session](https://developers.google.com/apps-script/reference/base/session)); выбор API верный, дефект именно в expiry policy.

У того же timeout есть обратная ошибка: если owner-trigger реально удалён, потерял доступ после смены владельца либо сломался, свежий marker заставляет все прочие триггеры молча уходить до трёх суток. Это прямой путь «кнопку не обслуживает никто». Переустановка новым владельцем лечит состояние, но автоматического обнаружения нет.

Отдельно установщик создаёт триггер **до** записи marker и возвращает `true`, даже когда `_invOwnerMarkWrite_()` вернул `false` (`Код.js:692-698`). В мастере предупреждающий toast через 800 мс заменяется toast следующего шага, а итоговый modal пишет «✅ Готово» и «триггер установлен». При недоступном `PropertiesService` — явно допустимом условии пакета — старые сотруднические триггеры продолжают исполняться, а владелец получает полный успех настройки.

**Что исправить:** не использовать отсутствие дверных событий как доказательство смерти owner-trigger. Доверенный creator должен оставаться доверенным до явной переустановки/смены владельца; recovery следует делать отдельной явной процедурой либо независимым heartbeat, а не fail-open первого денежного клика. Ошибка записи marker не должна возвращать полный успех мастеру. Нужны тесты «здоровый owner, четыре дня без дверей, первый клик сотрудника» и «marker write failed через setupAll».

### HIGH-3 — Для `unk` берётся старый общий backup L/M, поэтому инвойс может молча уехать на прежний пакомат

**Где:** `Код.js:3700-3721`, `Код.js:10843-10853`, `Код.js:13721-13745`

L/M не являются типизированным полем «резерв магазинного клиента». Существующий писатель Базы сохраняет туда прежние E/F при обычной смене адреса или способа доставки (`Код.js:3700-3721`). То есть в L/M может лежать исторический адрес любого клиента.

Новые callers, однако, спрашивают `_baseReserveOf_()` не только для `Dz70/IXO`, но и когда текущий основной способ имеет вид `unk`. Это превращает историю в активный источник без подтверждения:

- вчера у клиента был `OMNIVA` и адрес A;
- форму сохранили с новым текущим адресом/способом «Другое»; старые `A/OMNIVA` уехали в L/M;
- сегодня основной F классифицируется как `unk`;
- вместо честного `need_delivery`/формы новая ветка молча строит инвойс на старый A/OMNIVA.

Документ содержит формально узнаваемый тариф и адрес, поэтому никакая последующая проверка не отличает его от правильного. Это хуже прежнего fail-closed поведения для `unk`.

Тест раздела 43 проверяет `_baseReserveOf_()` изолированно и регуляркой закрепляет `need_delivery` только при `!_rsvSvc`; он не создаёт контакт с текущим `delv:'Другое'` и историческим L/M и не проверяет, что форма всё ещё открывается.

**Что исправить:** применять L/M автоматически только при доказанном текущем магазинном способе. Для `unk` сохранить прежний честный отказ и предложить форму с найденными данными. Если продукт действительно хочет использовать историю и для `unk`, это должно быть отдельное явное решение человека с показом текущего и прежнего адресов, а не автоматический fallback.

### HIGH-4 — Пользовательское меню обходит резервную развилку и создаёт другой документ, чем checkbox и приложение

**Где:** `Код.js:482-484`, `Код.js:8998-9016`; ядро `Код.js:7972-8009`

`createInvoicesForChecked()` — прямой пользовательский вход «Инвойсы → Создать инвойс». Он находит контакт, но вызывает ядро с `forcedContactData=null`:

```js
createInvoiceForClientFromRow_(sh, r, null, ...)
```

Ядро повторно читает основной контакт из Базы и не знает, что для магазинного клиента надо выбрать L/M. Поэтому один заказ даёт разные результаты в зависимости от входа:

- checkbox и `doPost` передают `_forcedE/_forcedSvc` и строят инвойс по резервному пакомату;
- меню передаёт `null`, использует основные `addr/delv = магазин/Dz70/IXO` и продолжает создание документа.

Для IXO ядро считает такой контакт pickup; для Dz70 строка даже не совпадает с внутренней проверкой `/(veikals|ixo)/`, поэтому может пройти как обычная доставка с магазинными реквизитами. Файл получает настоящее имя инвойса и попадает в рабочую папку — его можно принять за клиентский и отправить.

Это непосредственный caller изменённого ядра и сама основная команда меню, а не удалённый несвязанный путь. Тесты проводки резерва проверяют только `invStartForRow_` и `doPost`; `createInvoicesForChecked()` в разделе 43 отсутствует.

**Что исправить:** централизовать решение «основной контакт / магазинный резерв / форма / отказ» перед ядром либо внутри него, чтобы все три входа получали один результат. Добавить исполняемый тест одного магазинного контакта с L/M через checkbox, web и меню и сравнить фактически переданные ядру реквизиты.

### MED-1 — Cleanup защёлки исправлен только для занятого lock; сбой чтения/удаления всё ещё молча съедает следующий клик

**Где:** `Код.js:10445-10456`

При `tryLock(false)` функция теперь действительно пытается удалить свой marker без lock. Но если `getProperty()` падает, внутренний `catch` превращает результат в `null`, удаление не выполняется и даже запись в Logger отсутствует. Если падает `deleteProperty()`, остаётся только скрытый log. В обоих случаях marker живёт до TTL.

Когда Properties снова отвечает, следующий настоящий клик той же двери видит свежую чужую запись, получает `mine:false` и молча завершается. То есть MED прошлого ревью закрыт только для одного из трёх отказов cleanup.

Новый тест проверяет, что `getThrows`/`delThrows` не бросают исключение, и отдельно проверяет следующий клик только после **успешной** уборки. Последовательности `cleanup storage failure → storage restored → next click` нет.

**Что исправить:** как минимум сделать отказ cleanup видимым пользователю и не объявлять полную гарантию «следующее нажатие обслуживается» для непроверенного удаления. Добавить тест восстановления хранилища и повторной двери после каждого отказа cleanup.

### MED-2 — Batch replay не считается ни успехом, ни отказом, поэтому финал показывает зелёное «✅ Создано 0 из 1» без причины

**Где:** `Код.js:9016-9030`, `Код.js:9079-9086`

Ветка `_resB.ok && _resB.replay` правильно не увеличивает `created`, но также не добавляет строку в `failed` и не ведёт отдельный видимый счётчик replay. При одном отмеченном заказе итог:

- `checked = 1`;
- `created = 0`;
- `failed.length = 0`;
- выполняется зелёная ветка `✅ Создано инвойсов: 0 из 1`.

Причина и инструкция «снимите и поставьте галочку» остаются только в Logger/скрытом листе. Владелец видит зелёный итог, но не узнаёт, почему документ не появился и что делать. Тест раздела 13 проверяет регуляркой лишь отсутствие `created++` в replay-ветке и не исполняет финальный toast.

**Что исправить:** вести отдельный список `replayed/notCreated`, показывать предупреждающий итог и действие либо задать вопрос о подтверждённом повторе прямо в batch path.

## Ответы на вопросы пакета

1. **Есть ли путь, где кнопку не обслуживает никто?** Да. Свежий marker при удалённом/потерявшем доступ owner-trigger блокирует остальные аккаунты до трёх суток. Сбой cleanup дополнительно может молча поглотить следующий клик на 90 секунд.
2. **Может ли owner-gate заблокировать владельца?** После штатной установки текущего владельца — нет, сравнение email нормализовано. При смене владельца или оставшемся marker прежнего владельца — да, пока новый владелец явно не переустановит триггер либо marker не протухнет. В Shared Drive/при пустом email код чаще не блокирует, а отключает защиту fail-open; это возвращает много исполнителей. Копия безопасна только если setup действительно перезаписал marker; рассчитывать на это после ошибки Properties нельзя.
3. **Может ли `repeatOk` привести к лишнему документу?** Да. Повтор того же подтверждённого POST после потерянного ответа создаёт ещё один файл. Два последовательных исполнения с тем же `attemptId` и `repeatOk=true` также оба получают право на `new`; guard закрывает только реальное перекрытие по времени.
4. **Безопасен ли резерв?** Для доказанного магазинного контакта с полными L/M новый путь строку Базы не портит, а отсутствие terminal id само по себе честно отражает отсутствие сохранённого id. Но для `unk` L/M может быть старой общей историей, и тогда адрес выбирается молча. Меню резерв вообще игнорирует.
5. **Что стало хуже?** Owner-gate после обычного простоя снова выбирает сотрудника, а при живом marker и мёртвом владельце временно глушит всех. `repeatOk` сломал идемпотентность потерянного ответа. Резерв перевёл `unk` из честной формы/отказа в автоматический старый адрес и создал расхождение с меню.
6. **Мёртвый код и декоративные гейты?** Явно недостижимого нового production-кода не найдено. Декоративность находится в тестовых доказательствах: owner tests исполняют отдельные состояния, но не переход `fresh → idle → stale`; repeat test не закрывает и не повторяет подтверждённую попытку; reserve test проверяет два caller регулярками и пропускает третий; batch test не исполняет финальный UI.

## Решение по приёмке

**BLOCK.** Минимум до следующего круга:

1. вернуть идемпотентность подтверждённому повтору через отдельный стабильный id попытки;
2. убрать зависимость авторизации owner-trigger от частоты дверных событий и не считать установку полной при незаписанном marker;
3. ограничить автоматический резерв доказанным магазинным способом и провести ту же развилку через пользовательское меню.

MED-находки не создают неправильный документ напрямую, но обе сохраняют заявленные «молчащие отказы» и должны быть явно приняты владельцем, если по правилам позднего круга их решено не чинить.
