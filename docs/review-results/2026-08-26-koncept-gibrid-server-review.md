## Совпавшие CRIT

1. **Фолбэк по таймауту = два издателя документа.** Сервер сделал PDF и записал его себе, ответ
   потерялся; Apps Script уходит прежним путём и делает вторую таблицу с тем же номером. `attemptId`
   дедуплицирует обращения к серверу, но не второго, локального изготовителя.
   - Фейбл: сервер НИКОГДА не публикует — рендерит в staging/под черновым именем, а «настоящим»
     файл делает Apps Script после записи журнала (как сегодня «filled_draft → журнал → имя»).
   - Кодекс: издатель в каждый момент ровно один. Вариант A — сервер отдаёт PDF-байты, файл создаёт
     Apps Script. Вариант B — сервер единственный издатель, запрос становится durable job, локальный
     фолбэк запрещён, при неизвестном состоянии — честный отказ.
2. **Идемпотентности по одному `attemptId` мало.** Метка стабильна (локальная — 30 минут, складская —
   до полного успеха), а состав заказа между попытками меняется: сервер вернёт PDF со СТАРЫМ составом,
   который Apps Script финализирует как свежий. Ключ обязан включать состав: `attemptId + invoiceNo +
   sig` (Фейбл) или `sourceId + orderUid + generation + requestHash + версия шаблона` (Кодекс).
3. **Права на файл в Drive.** Владелец — обычный @gmail.com; передать владение из сервисного аккаунта
   нельзя, Shared Drive без Workspace нет. Файлы остались бы в квоте сервисного аккаунта (15 ГБ) и
   числились чужими, а `_invFileState_`/`_invReleaseDoc_` их бы не проверили. Фейбл (CRIT): работать
   OAuth-токеном владельца, то есть его доступ к Drive лежит на VPS. Кодекс (HIGH): до production —
   интеграционный spike на реальных папках «Италия»/«Скидки».

## Прочее, что назвали

- **У `UrlFetchApp` нет таймаута** (Фейбл, CRIT): «не ответил за N секунд» нереализуемо; при зависшем
  соединении работник ждёт минуту, и только потом начинается прежний путь на 19 с.
- **Привратник и журнал зашиты на URL Google-таблицы** (`Код.js:7768`, `4975`, гейт
  `test-invoice-release-gate.js`): PDF живёт по другому адресу, значит этап 1 обязан править сам рубеж
  десяти кругов. Кодекс требует типизированный `artifact` (fileId, MIME, invoiceNo, orderUid,
  generation, requestHash, templateVersion, pdfHash) и сверку манифеста в `_invReleaseDoc_`.
- **PDF — решение владельца, а не техники:** исчезает правка готового счёта руками; исправление
  становится `void/reissue`; ломается ссылка в кол. B (жёсткие spreadsheet-URL). Зеркало в «Собранные
  заказы» переносит тексты, а не документ, — само по себе не ломается.
- **Пул нельзя выключать, пока жив фолбэк** (Фейбл, MED): фолбэк — это прежний путь целиком.
- **Двойной счёт выигрыша** (оба, MED): 8–13 с посчитаны от баланса ДО правок 25.08.

## Оценка скорости

- Заявлено: 19 → 5–7 с после этапа 1.
- Фейбл: реалистично **~8–10 с**, выигрыш 5–8 с от НОВОГО баланса.
- Кодекс: ориентировочно **7–10 с**; «5–7 с возможно как лучший результат эксперимента, но не
  подтверждено». Заявленные 8–13 с — валовая стоимость удаляемого блока, не чистый выигрыш.

## Что оба советуют делать ВМЕСТО сервера (сначала)

- **Донор-таблица + `Drive.Files.copy`** — тот самый разрешённый путь из вердикта по концепту
  заготовки: ревизия ФАЙЛА донора доказывает свежесть, включая форматирование. Один RPC ~1–2 с
  (Фейбл) / исторически ~3,9 с (Кодекс) вместо `create + openById + copyTo + удаление листа + setName`
  (5–10 с).
- **Заполнение одним `Sheets.Spreadsheets.batchUpdate`** (Фейбл): значения, форматы, подложки и серые
  суффиксы через `textFormatRuns` — ~0,5–1 с вместо 3–5 с десятками вызовов SpreadsheetApp.
- Итог по Фейблу: ~9–11 с против ~8–10 с у сервера — «разница в пределах секунды-двух при несравнимой
  цене». Документ остаётся Google-таблицей, данные не покидают Google, привратник и журнал не
  трогаются, фолбэк тривиален, чинится из редактора.
