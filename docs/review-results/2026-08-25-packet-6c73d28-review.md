## Краткий итог

Патч исправил основной оборот `новая попытка → потерянный ответ → replay`, убрал expiry owner-marker, правильно ограничил автоматический L/M доказанным магазинным способом и провёл контактный plan через три входа. Обычный пакоматный клиент остаётся на `plan:'main'`.

Но новая передача reserve как `forcedContactData` выключает две прежние защиты денежного ядра:

- batch-меню больше не отказывает неоднозначному клиенту и может создать документ по первой тёзке;
- найденный контакт не связан со свежим владельцем строки, поэтому смена C между lookup и ядром даёт документ с товарами B и телефоном/пакоматом A.

Обе последовательности создают настоящий клиентский файл и сами по себе блокируют выкладку. Даже если применить правило пакета «в позднем круге MED/LOW только записываем», два CRIT требуют следующей заплатки.

## Findings

### CRIT-1 — Batch-меню обходит `ambiguous_client` и строит reserve-документ по первой тёзке

**Где:** `Код.js:9078-9102`, `Код.js:9128-9137`; ядро `Код.js:8046-8077`; тест `tests/test-shop-clients.js:2887-2930`

`createInvoicesForChecked()` получает весь результат `findContactWithHow_()`, но проверяет только наличие `lookup.contact`. Флаг `lookup.ambig` теряется. Если произвольно первый найденный контакт магазинный и имеет полный L/M, `_invContactPlan_()` возвращает `reserve`, а меню передаёт его как `forcedContactData`.

В ядре ambiguity-gate находится только в ветке без forced contact:

```js
if (forcedContactData) {
  contact = { /* доверенные реквизиты */ };
} else {
  const lookup = findContactWithHow_(key);
  if (contact && lookup.ambig) return { error:'ambiguous_client' };
}
```

До этого патча меню передавало `null`, поэтому именно ядро было его последней защитой. Новая проводка reserve эту защиту обошла.

**Воспроизведение:**

1. В Базе есть две разные `Anna Petrova` под одним слабым ключом.
2. Первая строка — магазинная, с телефоном и полным резервом L/M; заказ принадлежит второй.
3. `findContactWithHow_()` возвращает одновременно первый `contact` и `ambig:true`.
4. Владелец запускает «Инвойсы → Создать инвойс».
5. Меню строит forced contact из первой строки; ядро не повторяет lookup и создаёт файл с товарами второй клиентки и реквизитами первой.

При `plan:'form'` тот же пропуск предзаполняет форму данными произвольной тёзки; direct reserve-path хуже — человек вообще не получает точки остановки.

**Почему зелёный тест ничего не доказывает:** `runMenu()` возвращает `{contact, matchedBy}` без `ambig`, а денежное ядро подменено функцией, которая принимает forced contact без собственной проверки. Теста `ambig:true + shop + reserve` нет.

**Что исправить:** ambiguity должно быть частью единого контракта до plan либо проверяться в ядре и при forced contact. Нужен исполняемый тест, в котором меню при `{contact, ambig:true}` не вызывает ядро, не создаёт форму с чужими полями и снимает только свою галочку после свежей сверки строки.

### CRIT-2 — Reserve-контакт не связан со свежим владельцем заказа: гонка C `A → B` создаёт гибридный документ

**Где:** ядро `Код.js:7832-7905`, `Код.js:8046-8057`; меню `Код.js:9082-9088`, `Код.js:9137`; дверь `Код.js:11100-11115`; web `Код.js:13904-13966`

Все три изменённых caller сначала находят contact A и строят `_forced*`. Пока lookup ходит в Базу, владелец может поменять колонку C у того же номера заказа на B.

Последующие проверки не связывают forced contact с A:

- меню после lookup сверяет только галочку и номер заказа, но не C;
- обычная дверь L читает C, однако сравнивает её только при `_opt.expectedOwner`, а этот аргумент на обычном L-path отсутствует;
- `doPost` после lookup вообще не перечитывает C;
- меню и `doPost` вызывают ядро без `expectedOwnerIn`.

Ядро свежо читает уже B и честно доказывает лишь, что все свежие строки заказа принадлежат одному B. Затем forced-ветка без lookup принимает телефон и reserve A. Для одно-строчного заказа все существующие owner/order gates проходят.

**Воспроизведение:**

1. Строка заказа: номер `e7-101`, C=`anna`, найден магазинный contact A с L/M.
2. После `findContactWithHow_('anna')`, но до core-read, C меняют на `beata`; номер остаётся `e7-101`.
3. Core собирает товары и свежий ключ B, mixed-owner gate зелёный.
4. `_forcedA` подставляется без проверки и создаётся инвойс B с телефоном/пакоматом A.

Путь из «Собранных заказов» защищён, потому что передаёт `expectedOwner`; обычные L/menu/web — нет.

**Что исправить:** caller должен передавать исходный owner key во всех forced-вызовах, а ядро обязано fail-closed сверять его со всеми свежими строками. Ещё надёжнее — не считать caller-built contact доверенным: передать устойчивую identity-reference/строку Базы и заново подтвердить её после свежего чтения заказа. Нужны три interleaving-теста `lookup A → C becomes B → core` для menu, L и `doPost`.

### HIGH-1 — `repeatOk` принимается без `attemptId`, поэтому retry подтверждённого POST снова создаёт документ

**Где:** `Код.js:13773-13781`, `Код.js:13964-13966`, `Код.js:7512-7526`, `Код.js:7921-7931`, `Код.js:8836-8864`

Новый протокол безопасен только при непустой устойчивой метке попытки, но серверный контракт её не требует. `repeatOk:true` с пустым `attemptId`:

1. пропускает чтение надгробия, потому что `_attempt === ''`;
2. отключает `already_done` по колонке B;
3. создаёт новый инвойс;
4. не записывает надгробие и удаляет рабочую запись как у локального запуска;
5. при потере ответа тот же POST снова проходит и создаёт следующий файл без нового вопроса.

Текущая warehouse-страница метку обычно передаёт, но денежный сервер не должен fail-open принимать повреждённый, старый или частично сформированный клиентский запрос. Тест потерянного ответа моделирует только непустой `A1`; комбинации `repeatOk + empty attempt` нет.

**Что исправить:** как минимум в ядре `repeatOk && !_attempt` должен быть честным отказом. В web-boundary также нужно отвергать пустую/невалидную метку до lookup. Добавить полный оборот `already_done → repeatOk/no attempt → no file` и `repeatOk/A1 → close → retry A1 → replay`.

### HIGH-2 — После смены владельца owner-gate разрешает все старые триггеры, а не только нового владельца

**Где:** `Код.js:10518-10528`; тест `tests/test-door-once.js:199-218`

При transfer `boss → newboss`:

- старый boss проходит по раннему `me === mark.email`, не сверяя Drive;
- любой worker проходит, потому что текущий owner отличается от marker;
- marker не очищается и не заменяется.

До ручной установки trigger новым владельцем каждое событие снова обслуживают все старые triggers, а latch выбирает случайный первый аккаунт. Файлы опять могут создаваться от worker/old owner — исходный дефект owner-gate возвращается не на один клик, а постоянно.

Тест запускает только Katja и закрепляет `run` как желательный исход. Он не запускает на одном событии old owner, worker и new owner и не проверяет аккаунт созданного файла.

**Что исправить:** если настоящий owner известен и отличается от marker, `run` допустим только при `me === owner`; остальные должны `skip`. Новый владелец должен атомарно перепривязать marker/trigger либо получить явную инструкцию установки.

### HIGH-3 — Сбой чтения marker или пустая runtime-identity отключают owner-gate, хотя Drive может доказать чужой аккаунт

**Где:** `Код.js:10486-10498`, `Код.js:10513-10517`; тест `tests/test-door-once.js:220-231`

`_invOwnerMarkRead_()` сводит четыре разных состояния к `null`: marker отсутствует, JSON повреждён, `getProperty()` бросил, payload неполон. Gate на любом из них возвращает `run`. Пустые effective/active email также дают `run`.

Один transient Properties failure у старого worker-trigger позволяет ему первым взять latch и стать единственным исполнителем, хотя `_invSsOwnerEmail_()` мог бы подтвердить, что текущий аккаунт не владелец. Тесты изолированно утверждают fail-open body-call и не моделируют одновременный owner-trigger, worker-trigger и владельца файлов.

**Что исправить:** чтение marker должно иметь три исхода `found/absent/unknown`. Для `unknown` использовать Drive-owner fallback и разрешать только доказанному owner; если доказательства нет — видимый fail-closed, а не молчаливое открытие всех денежных дверей. Для пустого email устойчивее хранить trigger uid и сверять `e.triggerUid`.

### HIGH-4 — Дубли одного магазинного клиента с разными L/M дают адрес по порядку строк Базы

**Где:** `Код.js:1585-1593`, `Код.js:1613-1618`, `Код.js:1623-1633`, `Код.js:2572-2583`; тест `tests/test-shop-clients.js:2774-2787`

База прямо допускает дубли одной личности. `_sameIdentity_()` считает строки одним человеком по общему телефону или нику, а `_idxPut_()` ставит ambiguity только при другой личности либо другом **типе текущей доставки**. Новые `rsvAddr/rsvDelv` при конфликте не сравниваются.

Поэтому две shop-строки одного клиента с одинаковым телефоном/ником и разными валидными L/M считаются однозначными; в индексе остаётся первая. Сортировка Базы меняет, какой резерв `_invContactPlan_()` без вопроса передаст в настоящий документ.

Это новый денежный риск: раньше shop-клиент останавливался на форме, теперь конфликтующая история становится активным адресом.

**Что исправить:** для `plan:'reserve'` конфликт полных L/M у совпавшей identity должен давать ambiguity/form, если значения не совпадают точно. Пустой резерв можно безопасно уступить единственному полному, но два различных полных варианта выбирать по порядку нельзя. Добавить тест с двумя строками и повторить его в обратном порядке.

### MED-1 — После сознательного повтора следующий вопрос показывает первый, а не последний инвойс получаса

**Где:** `Код.js:6884-6887`, `Код.js:6900-6902`, `Код.js:7512-7550`, `Код.js:11115-11142`

Обычная локальная метка L неизменна 30 минут, а сознательный повтор теперь закрывается под отдельной A1:

1. L создаёт `R6-100`.
2. Второй клик replay-ит `R6-100`; по «Да» A1 создаёт `R6-101`.
3. Третий клик в том же bucket снова начинает с L и получает `R6-100`.
4. Диалог и тост «Оставил прежний инвойс» называют `R6-100`, хотя последним является `R6-101`.

Это регресс относительно `5ec4a84`, где подтверждённый повтор обновлял результат L. Новый тест проходит только `L → A1`; третьего клика `L → A1 → L` нет.

**Что исправить:** отдельно хранить latest-document pointer для UI либо после сознательного повтора ротировать локальную anchor-метку. Тест должен сделать три последовательных клика и проверять номер в третьем вопросе.

### MED-2 — Вечный owner-marker всё ещё допускает молча мёртвую дверь и неатомарное восстановление

**Где:** installer `Код.js:667-720`; reset `Код.js:10535-10575`; observer `Код.js:12776-12796`

Отказ от expiry правильно не путает отпуск со смертью trigger, но заявленная ручная recovery-схема не даёт надёжного обнаружения и атомарного восстановления:

- `warnMissingTriggers_()` видит только triggers текущего аккаунта. Worker со своим старым trigger получает «всё есть», даже если owner-trigger удалён; его onEdit затем молча `skip`, и дверь не обслуживает никто. Worker без своего trigger, наоборот, получает ложное предупреждение при здоровом owner-trigger.
- installer сначала удаляет свой старый trigger, затем создаёт новый и лишь потом пишет marker. Если `create()` падает, старый вечный marker остаётся, а выбранный им trigger уже удалён. Если marker-write возвращает `false` при ранее существовавшем marker, статус `no_mark` врёт: marker не отсутствует, а остался старый.
- reset читает marker, ждёт человеческий ответ и удаляет уже текущее значение без compare-and-clear. Пока окно открыто, owner может успешно записать новый marker; поздний YES worker удалит уже исправленную запись.

Сценарий «owner-trigger умер, worker-trigger существует» прямо отвечает на вопрос пакета: пункт меню помогает только после самостоятельной догадки; автоматический observer сообщает обратное.

**Что исправить:** marker должен содержать generation/trigger uid и состояние установки. Write/clear — под общим lock и с compare-and-clear. Installer должен либо завершить trigger+marker как одну подтверждённую операцию, либо откатить/явно пометить незавершённость. Observer должен проверять обслуживающий marker/owner, а не локальный список worker-триггеров.

### MED-3 — Cleanup latch сообщает только исключение, но не проверяет фактическое удаление

**Где:** `Код.js:10626-10652`; тест/мутации `tests/test-door-once.js`, `tools/mutations.js:1111-1124`

`deleteProperty()` вызывается, но read-back после него нет. Если удаление молча не состоялось, `_why` остаётся пустым: ни Logger, ни скрытого листа, ни toast. Следующий клик в пределах 90 секунд видит свежую запись и молча получает `mine:false` — ровно тот исход, который patch заявляет закрытым.

Есть и гонка fallback без lock: A читает свой id, B успевает под lock заменить запись новой арендой, затем A без compare-and-delete удаляет уже B. Третье исполнение может войти параллельно B.

Новые тесты моделируют `getProperty`/`deleteProperty` throws, но не `deleteProperty` без эффекта и не interleaving между read/delete. Мутация «отказ удаления снова молчит» убирает catch-log и ловится на exception-case; она не доказывает подтверждённое удаление.

**Что исправить:** после удаления перечитать property; оставшееся своё значение — видимый failure. Без lock нельзя реализовать атомарный compare-and-delete средствами PropertiesService, поэтому fallback должен как минимум не обещать взаимное исключение и иметь тестируемый безопасный протокол повторной проверки.

### MED-4 — L/M «подсказка» теряется до обеих боевых форм; тест сохраняет её только искусственным stub

**Где:** callers `Код.js:9106-9110`, `Код.js:11072-11077`; production pending `Код.js:2052-2064`; sidebar `Код.js:2148-2192`; warehouse `apps-script/web-app.js:9293-9304`, `apps-script/web-app.js:9528-9567`; тест `tests/test-shop-clients.js:2850-2930`

Callers передают `rsvAddr/rsvDelv`, но production `_pendMake_()` копирует в `rec.found` только `why/delv/name/phone/nick`. Sidebar reserve-поля не читает и не показывает. В web-ответе efir поля есть, однако текущая warehouse-страница передаёт в `openNewClientForm()` только note/name/phone/instagram/requirePakomat; сама форма reserve-полей не знает.

Следовательно, в табличной форме остаётся только краткий toast, а в складской форме подсказка не видна вовсе.

Зелёный тест ложноположителен: `runDoor()` и `runMenu()` подменяют `_pendMake_` на `{..., found: found || null}`, тем самым сохраняют поля, которые production отбрасывает. `doPost` проверяется проводкой/regex, но реальный consumer не исполняется.

**Что исправить:** либо сохранить и явно отрисовать оба поля в pending/sidebar и warehouse hint, либо убрать заявление о подсказке. Нужен интеграционный тест настоящих `_pendMake_ + showClientSidebarForPending_` и server-response → `openNewClientForm`.

### LOW-1 — `_invRepeatAttempt_` не уникален между параллельными V8 executions

**Где:** `Код.js:6900-6902`; тест `tests/test-repeat-invoice-guard.js:1316-1327`

Метка состоит из получасового локального ключа, `Date.now()` и счётчика на объекте функции. В каждом отдельном Apps Script execution счётчик начинается с 1. Два контекста для одного заказа в одну миллисекунду получают одинаковую строку и могут схлопнуть два отдельных подтверждения в один replay.

Тест вызывает функцию дважды только в одном VM-контексте и доказывает лишь локальный рост `seq`.

**Что исправить:** использовать UUID/достаточную случайность и тест с двумя независимыми VM-контекстами при одинаковом `Date.now()`.

## Ответы на вопросы пакета

1. **Один заказ получает второй документ без второго вопроса?** Да: авторизованный `repeatOk:true` без `attemptId`, затем потерянный ответ и retry создают ещё один файл. При корректной непустой новой метке штатный оборот исправлен: повтор той же попытки replay-ит прежний файл.
2. **Старая аппка без renewal метки?** Дубликат безопасно не создаёт: после «Да» тот же attempt снова получает replay. Но сознательный повтор фактически не работает и может зациклиться на прежнем ответе/вопросе. Поэтому warehouse с `pinvAttemptRenew_` должен быть выложен раньше efir либо сервер должен явно отклонять несовместимую версию.
3. **Есть путь, где дверь не обслуживает никто и человек не узнаёт?** Да: вечный marker + удалённый owner-trigger + сохранившийся worker-trigger. Observer видит локальный worker-trigger как исправный, а сам trigger молча `skip`.
4. **Границы `_invContactPlan_`?** Для одиночного контакта они корректны: `shop + полный pak-reserve → reserve`, `shop без полного reserve → form`, `unk → form`, обычный pak → main. Дыры возникают до/после plan: ambiguity меню, конфликт L/M у дублей и отсутствие owner-binding forced contact.
5. **Обычный пакоматный клиент?** Его plan остаётся `main`; reserve не подставляется. В проверенных caller-path отдельной регрессии main-клиента не найдено.
6. **Что хуже против `5ec4a84`?** Forced reserve обходит ambiguity-gate и открывает новый TOCTOU с гибридным документом; после сознательного повтора локальный UI снова привязан к первому документу получаса; конфликтующие L/M теперь автоматически становятся активным адресом.
